Compiler correctness · loop lowering

solve_for_interval mishandles min/max of booleans

A missing De Morgan case in SolveForInterval makes trim_no_ops shrink a serial loop to a single iteration — a silent wrong-output miscompile. One localized fix; full local suite green.

bug Halide::Internal main @ d33fd254f LLVM 21 arm-64-osx

01 The defect

A negated boolean min solves to the wrong interval

SolveForInterval (src/Solve.cpp) implements visit(And), visit(Or), visit(Not) and visit(Select), but not visit(Min) / visit(Max). Boolean min/max — the &&/|| encodings that and_condition_over_domain and the simplifier both emit — aren’t recognized as connectives, so Not fails to distribute over them.

Since min(x<0, x<2) ≡ x<0, the negation ≡ x>=0, so it must solve to [0, +∞):

Expected
[0, +∞)
Actual
[2, +∞)

It behaves as if !min(a,b) were !a && !b instead of !a || !b. Downstream, trim_no_ops builds a loop’s no-op condition by relaxing over inner loops with and_condition_over_domain (producing exactly such a min), then trims via solve_for_outer_interval — so a serial loop gets trimmed to a single iteration and real work is dropped. A wavefront/diamond-tiled recurrence with a GuardWithIf (likely) split tail over a non-tile-multiple extent then produces wrong output under parallelism.

03 Pull request · the fix

Treat boolean min/max as And/Or

Add visit(Min)/visit(Max) to SolveForInterval, rewriting a boolean min → And and max → Or and re-solving — exactly as the existing visit(Select) already does — so Not distributes correctly.
